Information Security Policy

Feed Your Head Farm LLC (DBA Garden Faery)
Version 1.0 · Effective May 25, 2026
Owner: Taylor Burnsed, Sole Member · taya@gardenfaery.love
Review cadence: Annually, or upon material change to systems

1. Scope

This policy covers all systems, data, and processes used by Feed Your Head Farm LLC ("the Company") to operate the Garden Faery Studio bookkeeping admin and any connected third-party services (PocketBase backend, Plaid, Square, Twilio, SimpleFIN, Stripe, etc.).

The Company is a single-member LLC. The sole member, Taylor Burnsed, is also the sole employee and the sole user of all systems described below.

2. Roles and Responsibilities

  • Information security owner: Taylor Burnsed (sole member)
  • All access requests, security incidents, and policy questions: taya@gardenfaery.love
  • Annual policy review: Taylor Burnsed

4. Access Control

  • The Garden Faery admin is single-user. Only the sole member has credentials.
  • VPS shell access requires an SSH ed25519 key with passphrase. Password-based SSH is not permitted.
  • PocketBase superuser access requires email + password authentication.
  • API secrets (Plaid, Square, Stripe, Twilio, SimpleFIN) are stored as systemd Environment= directives on the VPS and in a local password manager. Secrets are never committed to source control or shared in chat/email.
  • Third-party vendor accounts (Plaid Dashboard, Stripe Dashboard, etc.) have unique passwords stored in a password manager and have multi-factor authentication enabled where the vendor supports it.

5. Authentication

  • Strong, unique passwords are generated and stored in a password manager for every account.
  • Multi-factor authentication is enabled on the password manager itself and on every vendor account that supports it.
  • SSH access to production servers uses public-key authentication (ed25519). Private keys are stored only on the sole member's primary workstation, protected by a passphrase — this constitutes phishing-resistant multi-factor authentication (something the user has plus something the user knows).

6. Data Handling

In transit. All web traffic between client browsers, the admin, the PocketBase backend, and third-party APIs is encrypted via TLS 1.2 or higher. Let's Encrypt certificates are auto-renewed on the VPS via Caddy.

At rest. The PocketBase database file resides on Oracle Cloud Block Storage, which encrypts all data at rest with AES-256 by default. Backups inherit the same encryption-at-rest protections as the live database. Restricted credentials are never written to plaintext logs.

7. Endpoint Security

  • The sole member's primary workstation runs current macOS with FileVault disk encryption enabled and automatic security updates.
  • The workstation requires password / Touch ID authentication.
  • The workstation does not host production data; all data lives on the VPS.

8. Backups and Continuity

  • PocketBase data is backed up nightly to /opt/pocketbase/pb_data/backups/ on the VPS via an automated cron job that takes an atomic SQLite snapshot of data.db and auxiliary.db, compresses them with gzip, and retains the most recent 14 days.
  • Backup files inherit the same encryption-at-rest protections as the live database.

9. Logging and Monitoring

  • PocketBase logs all admin authentication events and surfaces "login from new location" alerts to the sole member's email.
  • Application logs do not capture restricted credentials.
  • Logs are retained on the VPS and rotated by systemd-journald defaults.

10. Vulnerability Management

  • The VPS runs Ubuntu LTS with unattended-upgrades enabled for automatic security patching (typically applied within 24 hours of upstream advisory publication).
  • End-of-life software is actively monitored and avoided across the stack (Ubuntu LTS, current PocketBase, current macOS).
  • Vendor dashboards (Plaid, Stripe, etc.) are reviewed periodically for security advisories.
  • Formal vulnerability scanning is not performed; risk is mitigated by minimizing the attack surface (no public write endpoints, admin-only access rules, minimal dependency footprint).

11. Incident Response

If a security incident is suspected (unauthorized access, leaked credential, suspicious activity on a vendor account):

  1. Contain: revoke the affected credential (rotate API keys, change passwords, terminate sessions).
  2. Assess: review logs to determine what was accessed.
  3. Notify: if consumer financial data may have been exposed, notify the affected vendor (Plaid, Square, Stripe, etc.) and any potentially affected individuals as required by applicable law.
  4. Document: record the incident, root cause, and remediation.

12. Data Deletion and Retention

  • Client records are retained for the duration of the client relationship plus a reasonable period for tax and compliance purposes (typically 7 years for financial records per IRS guidance).
  • A client may request deletion of their personal data at any time; records will be deleted within 30 days, retaining only what is required for legal/tax compliance.
  • Plaid access tokens are deleted when the corresponding bank connection is removed.
  • Backups are pruned to retain a rolling 14-day window appropriate to recovery needs.
  • This policy is reviewed annually alongside the rest of this document.

13. Third-Party Data Sharing

The Company does not share data collected via Plaid, Square, Stripe, or any other vendor with third parties, except as required to operate the Company's own bookkeeping and tax preparation. Vendors process their respective data under their own published terms.

14. Review and Changes

This policy is reviewed at least annually by the sole member, or sooner upon any material change to the systems, vendors, or data flows described above.

This policy is proportionate to the Company's size (single-member LLC, single user, internal bookkeeping use case) and is updated as operations evolve. Questions: taya@gardenfaery.love.
